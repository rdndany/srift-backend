# SolRift: complete project overview (for AI agents and new contributors)

This file explains what the project is, what is built today, how the code is organised, how the pieces talk to
each other, how to run and test it, and which rules and pitfalls to respect. Read it first, then read the
design docs it points to when you touch a specific area.

Last updated: Nov 10, 2026, after the rename to SolRift, the expansions list, 100-player crowds, and after fire, enchanting (table, anvil, enchantments), Phase 3.6 (hardening), the XP/level feature, armor, the third-person view, the title screen with game modes (survival, creative, hardcore), villages and the world overhaul (caves, lava, dungeons, mineshafts, loot chests). Phase 3 is complete; Phase 4 (Solana payments) is next.

## 1. What this project is

**SolRift** is a browser voxel sandbox adventure in the classic block-building tradition: infinite seeded terrain,
mining, building, crafting, survival, mobs, day/night, weather, and multiplayer. Like an MMO it grows through
**expansions** (new bosses, instances, dungeons and zones; see `docs/EXPANSIONS.md`). It is meant to gain
**Solana payments and ownership** (cosmetics, land, a player economy).

Hard constraints (decisions made with the owner, do not change them without asking):

- **Original assets only.** No third-party game textures, sounds, models, names or branding. Game *mechanics* are
  not protectable, but all art and audio are generated procedurally from code. Never name another game in the
  product, the UI or the code. "SolRift" should be trademark-checked before launch.
- **Devnet first.** Anything on Solana targets devnet until an audit and legal review; mainnet is a later phase.
- **No paid RNG / loot boxes.** Every paid item is deterministic (legal risk).
- **Wallet optional.** The game is fully playable without a wallet. A wallet adds cloud saves, a persistent
  multiplayer identity and (later) purchases.
- **Server-authoritative.** In multiplayer the server owns all game state; the client is untrusted. The server
  will also own all money logic. Single-player worlds are sandbox only.
- **We never hold player private keys.** Login is a signature, not custody.
- **Progress is never stored on-chain.** Inventories and world edits are normal saves in our backend. Only
  things worth owning (cosmetic NFTs, plots, the $RIFT token) go on-chain, and only in Phase 5.
- **Next.js, not Vite**, for the web app. **SQL (SQLite in dev, Postgres planned for prod), not MongoDB.**

`docs/PLAN.md` is the original aspirational plan; some choices there were simplified. This is the reality:

### 3.4 `scripts` (E2E, Playwright, Chromium on the graphics card)

`e2e.mjs` builds the web app into `.next-test` (so it never clobbers a running `next dev`), starts a game server on
**:8788** (in-memory DB, `WORLD_SEED=1337`, `CHEATS=1`, `NO_MOBS=1`), an Adventure realm on **:8790** and the built web
app on **:3100**, then runs the 37 suites in order: `smoke, scenarios, gameplay, mobs, plants, bow, weather, saves, auth,
cloud, online, crowd, xp, armor, view, home, world, nature, recipes, shield, bed, building, dyes, villages, trading,
enchanting, anvil, fire, worlds, adventure, legacy, vehicles, redstone, character, map, identity, classes`. It stops at
the first suite that fails. `E2E_ONLY=online,cloud npm run test:e2e` runs a subset. Screenshots go to `./screenshots`.
(The `bow` suite is timing-based and has failed once in a full run without a code cause; it passes on re-run.)

**The browser (`scripts/browser.mjs`, `launchBrowser()`):** every suite starts its browser there. By default it is the
full Chromium (`channel: 'chromium'`) in a hidden window, drawing with the graphics card (`--use-angle=d3d11
--enable-gpu --ignore-gpu-blocklist`): about 165 frames a second at 1280x720, and all 37 suites in roughly a quarter of
an hour. If that browser cannot start it falls back to the software renderer and says so. Switches (environment):
`E2E_WATCH=1` opens a real window so the run can be watched, slowed by `E2E_SLOW` milliseconds per action (150 by
default); `E2E_RENDER=software` forces the old software renderer (SwiftShader), which draws about one frame a second:
game time then runs at a tenth of real time (the frame step is capped at 0.1 s), and anything that waits on game time
(crafting, cooldowns, drops) needs timeouts ten times as long. A real browser asks for `/favicon.ico`, which the game
does not have; `launchBrowser` answers that request itself so it is not counted as a console error.

**What the suites assume (keep them in step with the rules):** a new character of the plain game carries the Emberstone
(bar slot 2) and the map (bar slot 3); an Adventure character wakes in the Undercroft with nothing, and gets the map and
compass from Elder Maren, a weapon from Garrick and the Emberstone from Brannoc. Drops are picked up only by walking onto
them: after `tickDrops(n)` a suite calls the `gatherDrops()` hook, which collects each drop as if the player stepped on
it. The result slot of a crafting grid is a preview until the Craft button (`[data-testid=forge-button]`, shift for
all) is pressed. Online nothing can be handed over from the page (`give`, `select` are single-player hooks): suites take
items from the creative inventory (`/gamemode creative`, the search box, shift-click) and press the number keys. The
title flow is play page, then who (guest or wallet), name and look, class, and straight into the game
(`scripts/titleFlow.mjs` has the shared steps). Seeds that are picked for a land (`villages.mjs`) drift when the terrain
generator changes; each village checks its biome first and says how to find new ones.

`scripts/loadtest.mjs` (`npm run loadtest`) is not part of E2E: it starts its own server and runs N simulated
players (section 6.5).

## 5. The core architecture: Realm, Player, GameSession

The most important idea: **one simulation, three hosts.**

```
                 packages/shared
        Realm (shared world)     Player (one person)
              \                      /
               \                    /
   GameSession = Player + its own Realm        GameRoom = one Realm + many Players
   (single-player, in the browser)             (multiplayer, on the server)
```

- **`Realm`** holds terrain access, generator, block entities, mobs and spawner, weather, drops, the player list,
  mob events and the day clock. `update(dt, activePlayers)` runs block entities, weather, crop growth (every 2 s),
  drops, mobs (targeting the nearest living player) and the spawner around living players. It also provides
  `emitAll`/`emitNear` for sounds/effects (volume attenuated with distance), `settleAround` for block updates and
  explosions, and `saveState`/`loadState` (time, weather, block entities).
- **`Player`** owns everything personal: body, inventory, vitals, menu/screen, mode (survival/creative), flying,
  mining progress, bow draw, respawn. `apply(Command)` handles discrete commands (select, scroll, drop, click,
  shift-click, open/close inventory, respawn, fly, home, mode). Gameplay commands are ignored unless the player is
  `ready` and no screen is open. `beginFrame/simulateStep/advance/advanceOne/postRealm/updateInteraction` drive the
  per-frame simulation at a fixed `STEP = 1/60` s. `savePlayer/loadPlayer` serialise progress.
- **`GameSession`** (single-player) ticks: commands, frame, `realm.update`, interaction, clock (the clock runs at
  1x while simulating, 0.2x while idle/paused).
- **`GameRoom`** (multiplayer) ticks the same objects at 20 Hz and never trusts timing from clients (section 6).

Because client prediction uses the same `stepPlayer`/`buildMove` as the server, the player's own movement feels
instant yet is checked by the server.

Single-player control flow in the browser: input -> `InputFrame`/`Command` -> `LoopbackLink` (still serialises to JSON
and validates, same path as a socket) -> `SessionHost` -> `GameSession` -> `SessionEvent`s -> audio/particles/UI.

## 6. Multiplayer (Phase 3.5) in detail

### 6.1 Server: `GameRoom`

- One `Realm` backed by `HeadlessWorld`; `members` map of connected players; default 120 players; ticks at 20 Hz.
- **Per tick:** for each member the time budget refills (`budget = min(0.25, budget + dt)`), commands from the
  member's queue apply immediately, and each queued **input** costs `STEP` (1/60 s) of budget (max 15 steps/tick).
  Each input runs `beginFrame`, `advanceOne` and (when no screen is open) `updateInteraction`. Dead players still
  step. Then `realm.update(dt, allPlayers)`, `postRealm`, `advanceClock`. Then block-change batches (`blocks`) and, per
  member, `events` followed by a `snap` snapshot.
- **Anti speed-hack:** the budget means a client can never advance faster than real time, however many inputs it
  sends. Input sequence numbers are deduplicated; the queue is capped at 240.
- **Join:** `joined {id, name, seed, tickHz, time}`, then `edits` batches (all world changes relative to the generated
  terrain, 6000 numbers per message, last has `last: true`), a `notice` to others, and a first state. Duplicate names get
  a number suffix. Over capacity -> `kicked "server full"`. A signed-in account already playing -> `kicked`.
- **Chat:** token bucket of 5 messages per 2 s per player. `/help /who /home` always work; `/time /weather
  /gamemode /tp` need `CHEATS=1`. A `mode` command from a client is rejected unless cheats are on.
- **Interest management:** snapshot radii 160 blocks for players, 96 for mobs and arrows, 64 for drops. The inventory
  view (36 slots, menu slots, cursor, furnace state) is sent only when it changed.
- **Persistence:** with a store (the default via `SqliteRepo.room`), edited chunks (compressed), world state (clock,
  weather, block entities) and the progress of **signed-in** players are saved every 30 s, when a player leaves and when
  the server stops. Guests are not persisted. One session per account at a time (prevents duplicating items). Chunks
  and state are keyed by seed, so a different seed is a different world.

### 6.2 Wire protocol (`netProtocol.ts`, JSON, protocol v1)

Client to server: `join {name}`, `input {frames: NetInput[<=8]}` (each `NetInput` has `seq, yaw, pitch, forward,
strafe, jump, sprint, sneak, left, right`), `cmd {c: Command}`, `chat {text}`, `leave`.

Server to client: `joined`, `edits {blocks, last}`, `blocks` (flat `[x,y,z,id,...]`), `snap` (tick, ack, time, weather,
`you: SelfView`, optional `inv`, `players`, `mobs`, `arrows`, `drops`), `events`, `chat`, `notice`, `kicked`.

`parseNetClientMessage`/`parseNetInput` validate and clamp everything (finite numbers, ranges, array lengths). Names are
sanitised to letters, digits, space, `_ . -` (max 24); chat has control characters stripped and is capped at 200
characters. The older `hello/ping/welcome/pong` messages (`protocol.ts`) are kept for the status ping; `server.ts` checks
those first, then the game messages. Constants: `NET_STEP_HZ=60`, `MAX_INPUTS_PER_MESSAGE=8`.

### 6.3 Client: `RemoteSession`

- **Prediction:** inputs are generated at fixed 1/60 s with increasing `seq`, each predicted locally with `stepPlayer`,
  queued in `pending`, and sent in batches of up to 8.
- **Reconciliation:** on a snapshot the body is set to the server state and unacknowledged inputs are replayed.
- **Smoothing:** other players, mobs and drops are exponentially smoothed; arrows are extrapolated.
- **Events** are held and dispatched after the snapshot that follows, so inventory data is current when the UI refreshes.
  Events arriving before the client is `ready` are dropped (the first snapshot carries the full state).
- **Menus** are mirrored: the same `Menu` class is built over mirror containers and the slot contents are overwritten from
  the server's `inv` view. Clicks are sent as commands.
- **No block prediction in v1:** placing/breaking shows after the server round trip. `World.applyRemoteEdits` stores edits
  per chunk and applies them to chunks generated later.
- `main.ts` connects and joins **before** creating the `World` (it needs the server's seed), skips local saves in online
  mode, sets `remote.ready = true` once the 5x5 chunks around the player are meshed, and shows other players with
  `PlayerRenderer`.

### 6.4 Known limits (as of 3.6)

No block prediction; only one room per server; the web client shows "reload to reconnect" instead of reconnecting by
itself; snapshots are full lists (not deltas), so bandwidth grows with the players and mobs in view; explosion
settle-drops are always on; the web client reads live-object views in single-player.

### 6.5 Hardening (Phase 3.6)

- **Most "cheats" cannot happen by construction:** the server runs every input, so speed (time budget), reach (`REACH`),
  mining speed, flying (survival) and noclip are server rules. Tests in `room.test.ts` ("is authoritative about") prove it.
- **Suspicion score** (`GameRoom.strike`, `STRIKES`): invalid message 5, forbidden command 3, chat spam 2, stale/replayed
  input 1, command flood 0.5, dropped input 0.1. Decays 1/s, warning at half the limit, kick at `kickScore` (default 50).
  Honest play scores 0. Commands are limited to 40/s (burst 60).
- **Connections** (`ConnectionLimits`): 10 open and 60 new sockets/min per address (X-Forwarded-For with `TRUST_PROXY=1`),
  join within 15 s, 20 invalid messages close the socket, 15 s ping/pong heartbeat drops dead connections (frees the
  account's single seat). **Back-pressure** (`sendWithBackpressure`): over 1 MB queued skips snapshots, over 8 MB disconnects.
  WebSocket `permessage-deflate` is on (3-4x less traffic).
- **Tick loop:** wakes every 12 ms and runs the ticks real time has earned (a plain 50 ms `setInterval` ran at 16 Hz on
  Windows, slowing the game by 20% and queuing inputs; the load test found this).
- **Metrics:** `GET /health` returns `room` stats (`tickMsAvg`, `tickMsMax`, `overruns`, `strikes`, `kicks`) and `memoryMb`.
- **Item safety:** `dupe.test.ts` fuzzes menus, drops and the shared chest with two players and checks that the item census
  never changes; disconnecting returns cursor items; dropped items on the ground are not persisted (a crash can lose them,
  never copy them); each save part (chunks, world state, each player) is attempted independently and chunk writes are transactions.
- **Load test results** (laptop, bots on the same machine, everyone in one spot, mobs on): 20 players 2.6 ms avg tick,
  32 KB/s per player; **100 players 11.5 ms avg tick (26 ms worst), 20 snapshots/s each, 72-77 KB/s per player on the wire,
  input ack p99 79 ms, 254 MB** (before the shared serialisation of players, see `docs/ACCOUNTS_AND_SAVES.md`; after it
  120 players cost 6.4 ms avg tick); 200 players overloaded one room back then (33 ms avg tick, 1.5 GB). Next optimisation: delta
  snapshots, a lower rate for distant entities, compact encoding.

## 7. Accounts, cloud saves and the save format

Full design: `docs/ACCOUNTS_AND_SAVES.md`. Summary:

- **Local saves (always):** IndexedDB (`LocalSaveStore`) holds edited chunks (RLE compressed) plus the player and world
  state records, all with a version `v` and migrations (old `localStorage` saves upgrade automatically). A save from a
  newer game version is refused ("Nothing was changed") and saves are frozen rather than overwritten. Export/import
  as `.solrift` files (header, CRC, compressed chunks) works for guests.
- **Sign-In With Solana:** `GET/POST /auth/challenge` -> wallet signs the SIWS message (Wallet Standard: Phantom,
  Solflare, Backpack) -> `POST /auth/verify` checks domain, nonce (single-use, 5 min TTL), timestamps and the ed25519
  signature, upserts the account, and sets an HttpOnly session cookie (opaque token, stored hashed, sliding 30-day
  expiry). `GET /auth/me`, `POST /auth/logout`. Accounts get a random public display name (`PlayerXXXXXX`); the wallet
  address is never shown to others.
- **Cloud saves (signed-in):** the browser copy is the working copy; only chunks edited since the last sync upload
  (60 s interval, on tab hide, "Sync now"). Revisions (optimistic concurrency, 409 on stale base), a 90 s write lease
  (423 if another holder), atomic transactional pushes, hostile-file validation, automatic backups (newest 6) with
  restore, limits (200 MB, 20 worlds, 30 writes/min per account), and conflict dialogs on the client. One cloud world per
  seed per account.
- **Multiplayer persistence:** separate tables (`room_chunks`, `room_kv`) hold the shared room world and signed-in
  players' progress (section 6.1).
- **Database today:** SQLite tables `accounts`, `sessions`, `cloud_worlds`, `cloud_chunks`, `cloud_backups`,
  `room_chunks`, `room_kv`. Interfaces (`Repo`, `CloudRepo`, `RoomStore`) keep a Postgres swap possible.

- **Experience and levels:** `Experience` (`packages/shared/src/experience.ts`) holds a level and the points into it, with the original curve (`xpToNext`: 2L+7 up to 15, 5L-38 up to 30, then 9L-158; `totalForLevel`) and a cap of 1000 levels. The world is cut into 96-block regions; (roughly one village per 430 by 430 blocks; F3 shows the nearest) a region holds a village with 60 percent probability at a hashed spot at least 30 blocks from its edge (so villages never touch), and is rejected unless a 3x3 sample (every 14 blocks) is dry (above sea level + 1), in plains, forest, desert or snow, and varies by at most 5 blocks; the village ground is the median height. The plan (cached per village) is a stone-brick plaza and roofed well, four gravel roads 14 to 24 blocks long, lamp posts, and buildings placed along the roads by rejection against a list of rectangles (kinds: small 5x5, large 7x6, farm 9x7, smithy 7x5, tower 5x5, stall 5x3, nothing farther than 28 blocks from the centre; `VillageGenerator.describe(site)` counts them). The buildings themselves live in `villageBuilders.ts`: a `Lot` maps lot coordinates (`i` along the road, `j` away from it, `dy` above the village ground) to the world so every routine is written once for all four road directions, and `house`, `farm`, `stall`, `tower`, `well` and `lampPost` write voxels `[x, y, z, id]` with the building blocks (doors facing the road, stairs and slabs for gable or flat roofs, fences, gates, trapdoor shutters, panes, ladders, coloured beds and wool). `styleFor(name, rand)` picks the materials: `VillageOptions.style(biome)` gives `oak` (planks, cobblestone foundation, oak or birch corner posts, wooden or cobblestone roof), `spruce` (snow and taiga) or `desert` (sandstone, chiseled corners, flat roof with a parapet). - **Rails and vehicles:** `rails.ts` gives every rail block (`B.RAIL_X`/`RAIL_Z` 48/49, curves `RAIL_ES..RAIL_EN` 1002-1005, slopes `RAIL_UP_*` 1006-1009, gold `POWERED_RAIL_X/Z` 1010/1011 and slopes 1012-1015; all non-solid 'flat' blocks that need a solid block under them) a `railInfo(id)`: two exits on cell edges (direction 0..3 = +x, -x, +z, -z and a height 0/1), a unit direction and a length. `wantedShape`/`railPlaced`/`railRemoved` reshape a rail and its neighbours (`Player.useHeldOn` and `Realm.settleAround` call them); every shape drops the one placeable rail item (`BUILDING_ITEM`). - **Redstone:** `BLOCK_COUNT` is 2048. Ids: `REDSTONE_ORE` 1016, `REDSTONE_BLOCK` 1017, `LAMP`/`LAMP_ON` 1018/1019, dust `WIRE_BASE` 1020 + signal 0..15, levers `LEVER_BASE` 1040, buttons `BUTTON_BASE` 1050 and redstone torches `RTORCH_BASE` 1070 (each base + face * 2 + on: face 0 = on the floor, face n = on the wall block in `BED_DIRS` direction n-1; `leverInfo`/`buttonInfo`/`rtorchInfo`/`mountSupport`/`mountedId`), plates 1060-1063 (`plateInfo`); item `I.REDSTONE` 389 (a non-block item placing `wireId(0)`; `REDSTONE_ITEM` in blocks.ts). Every state drops the one placeable item (`BUILDING_ITEM`/`NO_ITEM_BLOCKS`). `redstone.ts` holds the pure power model (`emitted`/`powerAt`/`isPowered`/`wireArms`/`wireLinks`: sources give weak power to their neighbours and strong power to the block they are fixed to, a conductor passes on only strong power, dust feeds the sides its arms point to; dust loops out only to blocks, never through wires of another network) and `RedstoneSim` (owned by `Realm.redstone`, ticked every 0.1 s from `Realm.update`): `notify(x,y,z)` (called by `Realm.blockChanged`, which replaced `fluids.notify` at every edit site, and by `settleAround`) queues a cell; a tick takes every dirty cell, recomputes the dust networks within two blocks (bucketed 15 -> 0 flood over `wireLinks`, capped at 3000 wires), applies lamps, doors (`Realm.setDoor`), trapdoors, gates and TNT (`primeTnt`) on a powered/unpowered edge, and flips torches (a torch reads the strong power of its support and changes on the next tick; eight flips in six seconds burn it out for two). Buttons keep a release timer, plates are pressed by players, mobs, vehicles and (wooden only) item drops from `Realm.pressers` and rise after a second; both are saved in `WorldState.redstone`. `Player.openForBlock` toggles levers and presses buttons. The mesher draws dust as flat quads (dot + arms, a wall strip on climbs, shaded by strength) and levers, buttons and plates as `shapes.ts` boxes. Tests: `redstone.test.ts`, `scripts/redstone.mjs`. - **Fire:** `packages/shared/src/fire.ts` is the model (`FireSim` on `Realm.fire`, `IGNITE_ODDS`/`BURN_ODDS` tables per block, `isFlammable`, `canFireStay`). Block `B.FIRE` = 173 (`cross` cutout, replaceable, hardness 0, light 15, no item; four animation tiles `fire_0..3` that the chunk shader cycles with `uTime`). Item `I.FLINT_AND_STEEL` = 383 (durability 64; shapeless iron ingot + flint); `Player.strikeFlint` lights the targeted face. Each fire ticks every 1.5-2 s with an age 0..15: it burns neighbours (300 sides / 250 up-down odds), spreads into nearby air (dx,dz -1..1, dy -1..4 with odds `(ignite+40+14)/(age+30)`), and dies when it has nothing to stand on or burn, on bare ground after age 3, at age 15 (1 in 4), in rain (`world.surfaceY` exposure), or when water reaches it (`FluidSim.washable`). Only fires within `FIRE_RANGE` (96) of a player tick; at most 250 per update. Fires in loaded chunks are discovered by the `growPlants` scan (`onFire` callback to `FireSim.adopt`). ## 11. Rules, conventions and pitfalls for agents

**Conventions**
- Keep game rules in `packages/shared` (pure and testable). The web client must not own gameplay logic; the server must
  not import anything from `apps/web`.
- Shared code takes an injectable random source (`rand`) so tests are deterministic. Do not use `Math.random` in simulation
  code that tests or the server rely on.
- Every network/API message and every save file is hostile input: validate, clamp, size-limit and never trust types.
- Never put purchases or balances inside a save. Never let a single-player save flow into the economy.
- Tests accompany features; run `npm run typecheck` and `npm test` after edits, and the relevant E2E suite for UI/net work.
- When changing the wire protocol, update `netProtocol.ts` parsers, `room.ts`, `remote.ts`, the tests and
  `docs/ACCOUNTS_AND_SAVES.md`.
- After a phase, update `docs/PLAN.md` status, `README.md` (test counts, how to use) and the "as built" docs.

**Windows / PowerShell pitfalls (the development machine)**
- In double-quoted PowerShell strings `$name` followed by letters interpolates, and the backtick is an escape (`` `n ``
  newline, `` `r `` carriage return, `` `p ``/`` `R `` silently drop the backtick). When writing code containing `$` or
  backticks through scripts, prefer the file edit tools or single-quoted here-strings.
- `[IO.File]` APIs need absolute paths (the process cwd differs from the PowerShell location).
- Avoid `Set-Content` for non-ASCII text (encoding); write UTF-8 without BOM.
- There is no `wc`/`grep`; use PowerShell equivalents or `rg`.
- `next dev` may create `apps/web/AGENTS.md`; delete it.
- Do not broadly kill node processes (dev servers and E2E servers may be running).
- `node:sqlite` prints an ExperimentalWarning; that is expected. PowerShell may show it as a NativeCommandError; it is not a failure.
- The file-read tool can show stale content after scripted edits; verify with `Select-String` if in doubt.

**Naming/IP:** never add another game's names, textures or sounds, and never mention other games by name in the project. New art must be procedural or original.

## 12. Glossary

- **Realm:** the shared world simulation (terrain, mobs, weather, drops, clock).
- **Player:** one person's state and rules inside a realm.
- **GameSession:** single-player host = Player + its own Realm.
- **GameRoom:** multiplayer host on the server = one Realm + many Players.
- **HeadlessWorld:** world storage without rendering (server, tests).
- **WorldAccess:** the minimal world interface the simulation needs (`getBlock`, `setBlock`, `surfaceY`, ...).
- **SaveStore:** interface for local/cloud storage of chunks, player and world state.
- **SIWS:** Sign-In With Solana, a wallet-signed login message.
- **Lease:** the 90 s single-writer lock on a cloud world.
- **Snapshot (`snap`):** the per-tick view of nearby entities the server sends each player.
- **Reconciliation:** replaying unacknowledged predicted inputs after receiving server state.
- **Budget:** the per-player seconds-of-input allowance that stops speed hacking.
- **`__solrift`:** the `?debug` window hook used by E2E tests.

## Mob tiers and the creature target frame

Every creature kind has a tier (common, uncommon, rare, epic: the item rarities' names and colours) and a level, in `packages/shared/src/mobTier.ts`. A boss is an epic with a "Boss" tag, and a strong dungeon monster (`elite`) is shown one tier higher. A rare kind is worth 1.25x the experience and 1.25x the chance of a gear drop, an epic kind 1.5x (a boss keeps its own experience). The crosshair picks the creature in front of it (the nearest, alive, not behind an opaque block, up to 32 blocks; `apps/web/src/game/mobTargeting.ts`), and it stays the target for 6 seconds after looking away. The frame (`MobTargetFrame` in `PlayerUI.tsx`, the same place as a player's frame, which wins when both are in view) shows the level, name, tier, a health bar with numbers and how it treats you (hostile, neutral, passive, quest giver, trader). The server sends `hp`/`mx` only for a hurt (or elite) creature and `el` for an elite; a client works out the full health of an unhurt one with `mobMaxHealth`.


## Rift events

A **rift** is a timed co-op world event: a tear opens 45-80 blocks from a player, a column of light marks it, and waves of monsters come out of it until the players seal it (or it collapses). Switched on by `RealmOptions.rifts` (the server enables it whenever natural spawning is on, `RoomOptions.rifts` overrides; single player passes it unless `?nomobs` or `?norifts`). It is off by default in `Realm`, so seeded tests are unaffected.

- **Rules** live in `packages/shared/src/rift.ts`: `RiftDirector` (own mulberry32 dice, so it never perturbs the realm's rolls), driven through a `RiftHost` (the realm implements it; tests use a fake). Grades: `uncommon` Faint (3 waves), `rare` Unstable (4), `epic` Raging (5), weights 60/30/10, the last wave of each has an elite warden (`Mob.elite`, health x4-5). Timeline: first rift 5 min after a player is about, then 15-25 min apart; omen 30 s -> fighting (a wave when the last is beaten, after 8 s; larger with more players at the rift, up to x2.5) -> `sealed` (paid) or `collapsed` (grade time limit of 7/9/11 min, or nobody within 48 blocks for 60 s: its monsters are removed). It stays on screen 25 s after the end.
- **Rift monsters** are `bound` + `guard` + `patrol` at the rift's centre, carry `Mob.rift` (the rift id): they do not burn in daylight and are never saved.
- **Credit and pay**: `Realm`'s `killed` hook calls `onKill` with the players within `KILL_CREDIT_RANGE` (the warden counts 3). On sealing, every player within 96 blocks with a kill or 20 s at the rift gets (`RIFT_GRADE_DEFS[g].reward`) xp, coins, a piece of gear for their class (rarity weights by grade) and sometimes a Glyph Tome.
- **Network/UI**: `Player.riftView()` -> `Realm.riftViewFor` (nothing in a dungeon copy, for spectators, or past 600 blocks) -> `SelfView.rift` -> `ClientSession.riftView()` -> store `rift` (`RiftHud`: plus distance and compass point) -> `RiftBlock` at the top of the quest tracker. `SessionEvent {t:'rift'}` (omen / open / wave / sealed / collapsed) shows a coloured banner and plays `audio.rift`. The beam is `apps/web/src/game/riftFx.ts`.
- **Testing/cheats**: `/rift [uncommon|rare|epic]` (cheats only); `?debug` hooks `startRift(grade)`, `riftState()`, `riftSkip(seconds)`, `riftKillAll()`. Tests: `rift.test.ts` (director with a fake host, and the realm), `room.test.ts`.
